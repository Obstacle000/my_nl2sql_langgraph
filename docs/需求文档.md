# 需求文档

> 上游：[立项文档](立项文档.md)。本文把 5 个场景展开成功能清单与验收条件。
> 数据库设计见 [数据库结构](数据库结构.md)，接口见 [接口文档](接口文档.md)。

## 1. 角色与边界

| 角色 | 能做什么 |
| --- | --- |
| 未登录用户 | 注册、登录 |
| 已登录用户 | 管理自己的数据源与数据集、问数、查看历史 |
| （不设管理员） | MVP 无后台管理，无跨用户可见性 |

**数据边界**：任何接口都必须以 `user_id` 为过滤条件；跨用户访问一律返回 404，不暴露资源是否存在。

## 2. 功能清单

优先级：P0 = MVP 必须；P1 = 二期；P2 = 后续规划。

### 2.1 账号

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| A1 | 注册 | 用户名 + 密码，bcrypt 存储，用户名唯一 | P0 |
| A2 | 登录 | 校验密码，签发 JWT（默认 120 分钟） | P0 |
| A3 | 身份校验 | 所有业务接口从 `Authorization: Bearer` 解析 `user_id` | P0 |
| A4 | 退出 | 前端删除 token；服务端无状态（不维护黑名单） | P0 |
| A5 | 改密码 | 旧密码校验后更新 hash | P1 |

### 2.2 数据源管理


| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| D1 | 新建 CSV 数据源 | 上传 CSV，自动建物理表并登记 | P0 |
| D2 | 新建 MySQL 数据源 | 填 host/port/user/password/database，凭证加密存储 | P0 |
| D3 | 测试连接 | 对 MySQL 源执行 `SELECT 1`，返回可读错误 | P0 |
| D4 | 同步 schema | 读取 `information_schema`，写入表/字段元数据并建索引 | P0 |
| D5 | 数据源列表 | 只列自己的；凭证脱敏（只回 host/port/database） | P0 |
| D6 | 删除数据源 | 级联删除数据集、元数据、物理表、Qdrant/ES 数据、缓存 | P1 |
| D7 | 定时同步 | 按天重新发现 schema，结构变化时 `schema_version + 1` | P2 |

### 2.3 数据集与元数据

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| M1 | 数据集列表 | 名称、描述、表数、schema 版本 | P0 |
| M2 | 查看表结构 | 表清单 + 字段（类型/角色/样例值/说明） | P1 |
| M3 | 字段描述维护 | 手工补充业务含义与别名，重建向量 | P1 |
| M4 | 指标配置 | 指标名、口径、依赖字段、别名 | P1 |
| M5 | 建向量索引 | 字段描述 + 别名 → Qdrant（payload 带 user_id/datasource_id） | P0 |
| M6 | 建全文索引 | 字段样例值 → ES（文档带 user_id/datasource_id） | P0 |

### 2.4 问数

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| Q1 | 三路召回 | 字段（Qdrant）、取值（ES）、指标（MySQL） | P0 |
| Q2 | 上下文组装 | 候选表 → 字段 + 样例值 + 主外键，转 YAML | P0 |
| Q3 | 生成 SQL | 表上下文 + 指标 + 日期 + 方言 + 原问题 → LLM | P0 |
| Q4 | 校验 | `EXPLAIN` 判断语法；错误写入 `error` | P0 |
| Q5 | 修正 | 失败后重写一次，**回到校验**（最多 1 次） | P0 |
| Q6 | 只读执行 | 仅 SELECT；行数上限 1000；超时 30s | P0 |
| Q7 | 流式返回 | SSE：`progress` / `result` / `error` | P0 |
| Q8 | 展示 SQL | 结果里带上实际执行的 SQL | P1 |
| Q9 | 多轮追问 | "那上个月呢" 基于上一轮 SQL 改写 | P2 |

### 2.5 缓存

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| C1 | 精确缓存 | 归一化问题 → hash → 命中直接执行 | P0 |
| C2 | 语义缓存 | 问题 embedding，cosine ≥ 0.95 且同源同版本才复用 | P0 |
| C3 | 只缓存成功 | 执行成功（`status=ok`）才写入 | P0 |
| C4 | 失效 | TTL 7 天；`schema_version` 变化自动换 key | P0 |
| C5 | 命中率统计 | 从 `query_history.hit_cache` 聚合 | P1 |

### 2.6 审计与安全

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| S1 | 问数审计 | 记录 user/dataset/问题/SQL/行数/耗时/状态 | P0 |
| S2 | 租户隔离 | 元数据、向量、全文、缓存全部带租户字段 | P0 |
| S3 | SQL 白名单 | 非 SELECT 直接拒绝；禁止多语句 | P0 |
| S4 | 凭证保护 | 加密存储、接口脱敏、日志不打配置 | P0 |
| S5 | 敏感列脱敏 | 手机号/身份证按规则打码 | P2 |

## 3. 关键流程

### 3.1 上传 CSV（D1 → M5 → M6）

```text
选择文件 → 校验（大小/编码/列名）→ 解析 → 生成物理名 ds{id}_t0
→ CREATE TABLE → 批量 INSERT → 写 dataset_tables / table_info / column_info
→ 建 Qdrant 向量 + ES 取值索引 → 返回 dataset_id
```

### 3.2 接入 MySQL（D2 → D3 → D4）

```text
填连接信息 → 加密保存 → 测试连接（SELECT 1）
→ 同步 schema（information_schema）→ 写元数据 → 建索引 → 状态置 ok
```

### 3.3 问数（Q1 → Q7）

```text
选数据集 → 查缓存 → 命中则直接执行
→ 未命中：召回 → 组装上下文 → 生成 SQL → 校验
   → 失败且未修正过 → 修正 → 再校验
→ 只读执行 → 返回结果 → 写缓存 → 写审计
```

## 4. 验收条件（每个 P0 功能）

| 编号 | 验收条件 |
| --- | --- |
| A1 | 重复用户名返回 409；密码入库为 bcrypt hash |
| A2 | 错误密码返回 401；正确返回可用 token |
| A3 | 无 token / 过期 token 返回 401 |
| D1 | 上传 115 行 CSV 后：物理表存在、`row_count=115`、元数据齐全 |
| D2 | 凭证入库为密文；列表接口不回密码 |
| D3 | 错误密码/端口返回可读错误而非 500 |
| D4 | 抽 10 张表，字段数与 `information_schema` 一致 |
| D5 | 两个账号互查对方数据源 → 404 |
| M5 | Qdrant 里能按 `user_id + dataset_id` 过滤到本数据集字段 |
| M6 | ES 搜索"华北"能命中对应 `column_id` |
| Q1 | 召回结果非空，且不含其他用户/数据集的数据 |
| Q3 | 生成 SQL 不含编造的表名/字段名 |
| Q4 | 语法错误时 `error` 非空且不中断图 |
| Q5 | 修正后的 SQL 会再校验一次；两次都错则不再循环 |
| Q6 | `DROP`/`UPDATE` 类 SQL 被拒绝；结果不超过 1000 行 |
| Q7 | 客户端能连续收到 progress 帧，最后一条为 result |
| C1 | 同一问题连问两次，第二次 `hit_cache=1` |
| C3 | 执行失败的 SQL 不会被缓存 |
| S1 | 每次问数都有审计记录，含耗时与状态 |
| S2 | 泄漏专项测试全绿 |

## 5. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 未命中 P95 < 5s；命中 P95 < 200ms |
| 并发 | 单实例 20 并发不报错；连接池 ≤ 10 |
| 安全 | 只读账号；SQL 白名单；凭证加密；租户过滤 |
| 可用性 | 单数据源故障不影响其他数据源（错误隔离） |
| 可观测 | request_id 贯穿日志；慢查询记录 `latency_ms` |
| 可维护 | 分层清晰；新增一种数据源只写一个类 |

## 6. 评测集规划（50 条）

| 类别 | 条数 | 例子 |
| --- | --- | --- |
| 单表聚合 | 15 | 上个月华北的销售总额 |
| 分组 + 排序 | 10 | 销量前 5 的品类 |
| 多表关联 | 10 | 各品类的退货率 |
| 时间窗口 | 10 | 最近 7 天每天的订单量 |
| 边界/错误 | 5 | 查不存在的地区（应返回空而非报错） |

```text
判定方式：生成 SQL 与标准 SQL 各自执行，比对结果集（行数 + 值）
指标：执行准确率 = 一致条数 / 总条数
```

**砍掉/延后**


**风险**

| 风险 | 应对 |
| --- | --- |
| 课业冲突 | 优先保 M1（基线）和 M6（可投递），中间功能可缩 |
| 微调效果不如 API | 保留 API 版做对比即可，结论本身就能讲 |

> 按依赖顺序排，**每个功能做完立刻跑 50 条评测集，记录准确率变化**——没有前后对比，功能再多也讲不出价值。

### R1 schema linking 优化（优先级最高，是地基）

| 项 | 内容 |
| --- | --- |
| 问题 | 现在召回是“关键词 top-k”，噪声大、漏字段，直接决定生成质量 |
| 做法 | ① 两阶段召回：先选表（表级向量）再选字段（表内字段向量）<br>② 候选带 score 排序后进 prompt<br>③ 主外键由规则自动补齐，不指望模型<br>④ 命中值单独标注，不与 examples 混在一起 |
| 改动 | `agent/nodes/recall.py`、`merge_retrieved_info`、`filter_table` 的 prompt、state 增加 `matched_values` |
| 验收 | 同一份 50 条评测集，执行准确率提升 ≥ 10 个百分点 |
| 工期 | 3~5 天 |

### R2 结果自检（执行后才做，和语法校验不同）

| 项 | 内容 |
| --- | --- |
| 问题 | 语法校验只保证“能跑”，不保证“答对”；错的答案用户看不出来 |
| 检查项 | 空结果、全 NULL、比例越界（>100%）、负数、金额量级异常、明细汇总不一致、行数异常 |
| 做法 | 新增节点 `check_result`（`run_sql` 之后）；不通过 → 回 `correct_sql` 或 `generate_sql`，最多 1 次 |
| 改动 | state 增加 `retry_reason` / `check_rounds`；图增加节点与条件边 |
| 验收 | 构造 10 条“SQL 能跑但结果不合理”的用例，≥ 7 条能被识别并修正 |
| 工期 | 2~3 天 |

### R3 歧义澄清（HITL）

| 项 | 内容 |
| --- | --- |
| 问题 | 口径不明时现在是猜（“退货率分母是订单数还是商品数”） |
| 做法 | 新增节点 `clarify` 判断是否需要澄清；`interrupt()` 暂停；用户选择后从检查点恢复 |
| 改动 | 启用 checkpointer（`AsyncSqliteSaver`/Postgres）；SSE 增加 `type=clarify` 帧；新增 `conversation` 表；前端弹选项 |
| 验收 | 5 条歧义用例，全部触发澄清；用户选择后能继续执行并得到正确结果 |
| 工期 | 4~6 天（HITL 与检查点是主要工作量） |
| 风险 | 依赖前端配合，否则只能命令行演示 |

### R4 多轮对话（依赖 R3）

| 项 | 内容 |
| --- | --- |
| 场景 | “那上个月呢”“只看华东”“再按品类拆一下” |
| 做法 | 会话表 + checkpointer 存历史；新增节点 `rewrite_question` 做指代消解与条件继承 |
| 改动 | state 增加 `conversation_id` / `history_sql`；接口从 `/api/query` 扩展为 `/api/chat` |
| 验收 | 10 条多轮用例（追加时间/追加维度/追加筛选），准确率 ≥ 60% |
| 工期 | 5~7 天 |

### 顺序与定位

```text
R1 → R2 → R3 → R4
做完 ①②：能讲“准确率从 62% 提到 78%”
再做 ③④：能讲“从单轮工具到对话式分析助手”
```

### 不做的

```text
微调模型、跨库联邦查询、BI 看板、移动端
```
