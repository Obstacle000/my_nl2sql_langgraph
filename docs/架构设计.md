# 架构设计

> 本文回答三个问题：**分层怎么分、一次操作怎么跑、出问题从哪查。**
> 上游：[需求文档](需求文档.md)；表结构见 [数据库结构](数据库结构.md)；接口见 [接口文档](接口文档.md)。

---

## 一、定位与约束

```text
多用户 NL2SQL：接入数据源（CSV / MySQL）→ 中文提问 → 生成 SQL → 只读执行 → 结果 + 缓存
```

约束（决定了后面所有设计）：

| 约束 | 影响 |
| --- | --- |
| 多用户 | 每张业务表、每次检索、每个缓存 key 都必须带 `user_id` |
| 多数据源 | 执行入口必须抽象，不能写死连自己的库 |
| 只读 | 执行用只读账号 + SELECT 白名单 |
| 单机部署 | 无消息队列；索引同步做或进程内后台任务 |
| 成本敏感 | 云端 embedding + LLM 调用要批量、要缓存 |

## 二、分层与依赖

```text
app/api/            接口层：路由、依赖注入、lifespan（唯一 new 具体实现的地方）
     │
app/services/       应用层：用例编排（auth / dataset / meta_index）
     │
app/agent/          LangGraph：state / context / graph（召回→生成→校验→执行）
     │
app/datasources/    数据源抽象：DataSource 协议 + CSV/MySQL 实现 + registry
     │
app/repositories/   数据访问：mysql / qdrant / es / redis
     │
app/clients/        连接管理：五个 manager（mysql/redis/qdrant/es/embedding）
```

| 层 | 回答什么 | 判断标准 |
| --- | --- | --- |
| api | 请求怎么进来、依赖怎么组装 | 出现 `Depends` / `HTTPException` |
| services | 一次操作怎么编排 | 说“先建源、再建数据集、再建索引”，不写 SQL |
| agent | 图怎么流转、分支怎么走 | 出现 `StateGraph` / `add_edge` |
| datasources | 不同来源怎么统一查 | 出现 `execute` / `discover_schema` |
| repositories | 数据怎么存取 | 出现 SQL / ES DSL / Qdrant filter |
| clients | 连接怎么建、怎么关 | 出现 `create_async_engine` / `AsyncQdrantClient` |

**装配点只有两处**：`api/lifespan.py`（应用级资源）、`api/deps.py`（请求级依赖）。

## 三、鉴权：两层结构

沿用 Java 的「Filter + Interceptor」思路：**第一层解析并续期，第二层校验并拒绝。**

```text
请求
 │
 ├─ 第一层：HTTP 中间件（永不拒绝）
 │    · 有 Bearer token 就解析 → user_id 写入 ContextVar
 │    · token 剩余 < 15 分钟 → 续签，塞进响应头 X-New-Token
 │    · 解析失败 → 按未登录处理（不报错）
 │    · 公开接口带 token 也会续签
 │
 ├─ 业务处理（函数内用 current_user_id() 取当前用户）
 │
 └─ 第二层：每个处理器的 Depends(get_current_user_id)
      · 函数签名里写 `user_id: CurrentUser` 即生效
      · ContextVar 为空 → 401
      · 不声明的接口（login/register）天然豁免
```

> **为什么分成两层**：续签是"只要有 token 就做"，拦截是"只对需要的接口做"。
> 合并会导致公开接口无法续签，或受保护接口忘记校验。

**为什么不用 ThreadLocal**：asyncio 单线程跑多协程，`threading.local` 会串数据，必须用 `contextvars.ContextVar`。

**为什么续期放第一层**：每个请求只解析一次，续期对业务代码透明。

## 四、主链路

### 4.1 接入 MySQL 数据源

```text
POST /api/datasources/probe
  │  测试连接（SELECT 1）→ 读 information_schema → 返回表清单（不落库）
  ▼
POST /api/datasources
  ├─ 加密 config（Fernet）→ 写 datasources(status=unknown)
  ├─ 测试连接
  ├─ 建 datasets（datasource_id 指向源）
  ├─ 只登记用户勾选的表 → dataset_tables
  ├─ discover_schema 明细 → table_info / column_info
  ├─ 建索引：字段描述+别名 → Qdrant；样例值 → ES
  └─ status=ok
```

### 4.2 上传 CSV

```text
POST /api/datasets/{id}/tables
  ├─ 解析（utf-8 → gbk 兜底）→ 类型推断 → 列名清洗
  ├─ CREATE TABLE ds{dataset_id}_t{n}  + 批量 INSERT
  ├─ 事务：dataset_tables / table_info / column_info
  └─ 建索引：Qdrant + ES（幂等，失败可重试）
```

> DDL 在 MySQL 里隐式提交，不能和元数据同事务；所以物理表先建、元数据后提交，索引最后。

### 4.3 一次问数（核心）

```text
POST /api/query
  │
  ├─ 第一层中间件    解析 token → ContextVar（可能需要续期）
  ├─ 第二层依赖      校验 user_id（401）
  │
  ├─ 路由
  │    dataset = DatasetRepository.get(user_id, dataset_id)   ← 越权即 404
  │    source  = registry.get(user_id, dataset_id)            ← 按数据集找数据源
  │
  ├─ StreamingResponse(stream())
  │    └─ graph.astream(state, context=ctx, stream_mode="custom")
  │         │
  │         ├─ check_cache     Redis 精确命中？命中直接 run_sql
  │         ├─ recall          ① Qdrant 字段向量（filter user+dataset）
  │         │                  ② ES 取值全文（filter user+dataset）
  │         │                  ③ MySQL 补指标依赖字段与主外键
  │         ├─ generate_sql    schema 上下文 + 指标 + 日期 + 方言 + 原问题 → LLM
  │         ├─ validate_sql    EXPLAIN → error
  │         │     └─(error 且 fix_rounds=0) correct_sql → validate_sql（再校验）
  │         ├─ run_sql         source.execute(sql, limit=1000, timeout=30s)
  │         └─ 写回缓存        仅当执行成功（精确 + 语义）
  │
  └─ yield f"data: {json}\n\n"
```

### 4.4 索引与检索的关系

```text
建索引（上传/同步时）                     检索（问数时）
  Qdrant: 字段描述 + 每个别名 → 向量      recall: 关键词向量 → top-k（过滤租户）
  ES    : 字段样例值 → 文档               recall: 关键词 match（过滤租户）
  MySQL : 表/字段元数据                   merge : 按 column_id 补全
```

## 五、关键设计决策

### 5.1 State 与 Context 分离

```text
State   会被检查点序列化、被 reducer 合并 → 只能放可序列化数据
Context 只在执行期存在 → 放 Repository、DataSource
```

### 5.2 三路召回各用各的存储

| 目标 | 存储 | 原因 |
| --- | --- | --- |
| 字段 | Qdrant | “销售额” ≈ `order_amount`，字面不重合 |
| 指标 | Qdrant | 业务口径说法不统一 |
| 取值 | ES | “华北”必须字面命中，否则 SQL 查不到；且能保证 examples 里是真实值 |

### 5.3 两级缓存

```text
精确：归一化问题 → sha256 → key 命中即复用
语义：问题 embedding，cosine ≥ 0.95 且同 user + dataset + schema_version 才复用
只缓存执行成功的 SQL；TTL 7 天；schema 变更靠版本号天然失效
```

### 5.4 DataSource 抽象

```text
上层只依赖 DataSource 协议（test_connection / discover_schema / execute）
→ CSV 与 MySQL 的差异收敛在各自实现里
→ 新增 PostgreSQL/ClickHouse 只写一个类 + 一个方言映射
```

### 5.5 物理表名程序生成

```text
用户文件名不可信（中文、空格、括号、重名、注入）
→ ds{dataset_id}_t{序号}；业务名另存 dataset_tables.table_name
```

### 5.6 修正后回到校验

```text
correct_sql → validate_sql → 通过才执行
fix_rounds ≤ 1，避免死循环；保证修正后的 SQL 也过校验
```

### 5.7 数据源连接池有上限

```text
每数据源一个 engine；registry 用 LRU 缓存最多 20 个，超了 dispose
→ 防 100 用户 × 5 源 = 500 个池把连接打爆
```

| MySQL Engine | 应用级 | `create_async_engine(pool_size=10)` |


## 七、安全设计

| 风险 | 措施 |
| --- | --- |
| 越权 | 所有仓储方法带 `user_id`；越权返回 404 |
| 跨租户召回 | Qdrant `Filter`、ES `filter`、Redis key 全部带租户 |
| SQL 注入/写操作 | 只读账号 + SELECT 白名单 + 禁止多语句 |
| 大结果拖垮 | `fetchmany(limit)` + 执行超时 30s |
| 凭证泄漏 | Fernet 加密存储；接口脱敏；日志不打 config |
| 密码泄漏 | bcrypt；不记录请求体中的 password |
| 缓存串数据 | key 含 `user_id + dataset_id + schema_version` |

## 八、可观测性

```text
request_id  中间件生成 → ContextVar → 日志每行带 rid
user_id     第一层解析后写入 → 日志带 uid
审计        每次问数写 query_history（问题/SQL/行数/耗时/状态/是否命中缓存）
指标（计划）缓存命中率、P95 延迟、错误率、索引耗时
```

## 九、排障对照表

| 症状 | 先查 |
| --- | --- |
| 401 | `JWT_SECRET` 是否一致、token 是否过期、中间件是否执行 |
| 上传 400 | CSV 编码（utf-8/gbk）、列名非法字符、大小/行数超限 |
| 连接失败 | 端口/host 可达性、只读账号权限、库名是否正确 |
| 召回为空 | 索引是否建成、Qdrant/ES 过滤条件是否带了 dataset_id |
| SQL 报 Unknown column | schema 是否过期 → 手动 `sync` |
| 查询结果为空 | 值是否真在库里、大小写/空格、日期格式 |
| 缓存从不命中 | 归一化规则、schema_version 是否变过 |
| 结果出现别人的数据 | 逐个检查 Qdrant filter / ES filter / SQL where / Redis key |
| 索引很慢 | 字段数 × 别名数 = embedding 次数；改批量或异步 |

## 十、已知限制与演进

```text
现状限制：
· 单机部署，无消息队列；索引同步执行，表多时慢
· 指标需手工配置，CSV 推断不出业务口径
· 无语义结果自检（只校验语法）
· 无多轮对话（不支持“那上个月呢”）
· 无 refresh token 轮换（滑动续期够用，但无法主动吊销）

演进顺序：
① 索引异步化（任务表 + 后台 worker + status=indexing）
② 结果自检（空结果/异常值 → 重试或提示）
③ 多轮改写（带上一轮 SQL 与结果）
④ 指标自动化（LLM 生成候选 + 人工确认）
⑤ 接 ClickHouse/Hive（多数据源的真正价值场景）
```
