# 数据库结构

> 所有元数据在 `nl2sql` 库（MySQL 8.0）；用户上传的 CSV 数据落在**运行时创建的物理表** `ds{dataset_id}_t{n}`。
> 时间统一 `BIGINT`（Unix 秒）；JSON 一律 `TEXT` 存字符串。
> 上游：[需求文档](需求文档.md)；接口见 [接口文档](接口文档.md)。

## 一、设计原则

```text
① 多租户：所有业务表带 user_id 或 dataset_id，查询必须过滤
② 三份存储各司其职：MySQL 存关系与行数据、Qdrant 存字段向量、ES 存取值的全文索引
③ 物理表名程序生成：ds{dataset_id}_t{序号}，绝不使用用户输入
④ 元数据 id 自带语义：字段是"表.字段"，指标是"{dataset_id}:指标名"
⑤ schema 变更 = schema_version + 1，旧缓存自然失效
⑥ 只读执行：查用户数据用只读账号，元数据表用可写账号
```

## 二、总览

| 模块 | 表 | 说明 |
| --- | --- | --- |
| 账号 | `users` | 用户与密码哈希 |
| 数据源 | `datasources` | 连接方式与加密凭证（CSV / MySQL） |
| 数据集 | `datasets` `dataset_tables` | 查询作用域 + 业务名到物理名映射 |
| 元数据 | `table_info` `column_info` `metric_info` | 供检索与提示词使用 |
| 审计 | `query_history` | 问数记录、缓存命中、耗时 |
| 用户数据 | `ds{dataset_id}_t{n}` | 每份 CSV 一张，或 MySQL 里的原始表 |

```text
users 1──N datasources 1──N datasets 1──N dataset_tables
                                  │
                                  ├──N table_info 1──N column_info
                                  ├──N metric_info
                                  └── 物理表 ds{id}_t0 ... ds{id}_tN
users 1──N query_history
```

## 三、表结构

### 3.1 users — 用户

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INT **PK** AUTO_INCREMENT | |
| `username` | VARCHAR(64) **UNIQUE** | 登录名，3~32 字符 |
| `password_hash` | VARCHAR(255) | bcrypt（60 字节），绝不存明文 |
| `created_at` | BIGINT | 秒级时间戳 |

索引：`uk_users_username (username)`

> 不用软删除：MVP 无用户注销；删除用户需要级联清理所有数据，二期再做。

### 3.2 datasources — 数据源

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INT **PK** AUTO_INCREMENT | |
| `user_id` | INT **FK→users.id** | 归属 |
| `kind` | VARCHAR(16) | `csv` / `mysql` |
| `name` | VARCHAR(128) | 展示名 |
| `config_enc` | TEXT | 加密后的 JSON（host/port/user/password/database）；`csv` 为空 |
| `status` | VARCHAR(16) | `unknown` / `ok` / `error` |
| `error` | TEXT | 最近一次错误信息（可读） |
| `last_checked` | BIGINT NULL | 最近一次测试连接时间 |
| `created_at` | BIGINT | |

索引：`idx_datasources_user (user_id, id DESC)`

> **为什么凭证要单独一张表**：连接信息只与“从哪连”有关，和“查哪些表”无关；
> 放在 datasets 里会导致改密码要更新多行，且容易在查询里被误带出来。
>
> **加密方式**：`cryptography.Fernet`，密钥由环境变量 `DS_SECRET_KEY` 经 sha256 派生；
> 接口返回时只给 host/port/database，日志永不打印 `config_enc`。

### 3.3 datasets — 数据集
- 模型：`datasources  ── N datasets`（`datasets.datasource_id` 外键）
- 实现：每次新建数据源，同时只建一个数据集 → 实际 1:1
- 用户创建数据源时后端返回表清单,用户勾选

| 字段 | 类型 | 说明                              |
| --- | --- |---------------------------------|
| `id` | INT **PK** AUTO_INCREMENT |                                 |
| `user_id` | INT **FK→users.id** | 归属                              |
| `datasource_id` | INT **FK→datasources.id** | 属于哪个源                           |
| `name` | VARCHAR(128) | 展示名(不是表名)                       |
| `description` | VARCHAR(512) | 说明                              |
| `schema_version` | INT DEFAULT 1 | 元数据变化时 +1                       |
| `created_at` | BIGINT |                                 |

索引：`idx_datasets_user (user_id, id DESC)`

> **数据来源类型**统一由 `datasources.kind`（`csv` / `mysql`）表达，datasets 不再冗余存一份。
>
> **schema_version 的用途**：进 Redis 缓存 key。加表/改字段后 +1，旧缓存自动不再命中，
> 不用手动清理。

### 3.4 dataset_tables — 物理表登记

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INT **PK** AUTO_INCREMENT | |
| `dataset_id` | INT **FK→datasets.id** | |
| `table_name` | VARCHAR(128) | 业务名（展示给模型/用户，如“订单”） |
| `physical_name` | VARCHAR(128) | 物理名（`ds1_t0`，MySQL 直连时等于真实表名） |
| `row_count` | INT | 写入时的行数 |
| `created_at` | BIGINT | |

索引：`idx_dataset_tables_dataset (dataset_id)`，唯一键 `uk_dataset_tables (dataset_id, physical_name)`

> **业务名 vs 物理名**：用户文件名不可信（中文、空格、括号、重名、注入），
> 物理名必须程序生成；MySQL 直连时两者相同，因为表名是 DBA 定的。

### 3.5 table_info — 表说明

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | VARCHAR(128) **PK** | 物理表名（`ds1_t0` / `orders`） |
| `dataset_id` | INT **FK→datasets.id** | |
| `name` | VARCHAR(128) | 业务表名 |
| `role` | VARCHAR(16) | `fact` / `dim` |
| `description` | TEXT | 表说明（进提示词） |

索引：`idx_table_info_dataset (dataset_id)`

> `role` 影响 JOIN 策略提示：事实表带外键与度量，维度表带主键与属性。

### 3.6 column_info — 字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | VARCHAR(160) **PK** | `表.字段`（如 `ds1_t0.amount`） |
| `dataset_id` | INT **FK→datasets.id** | |
| `table_id` | VARCHAR(128) | 指向 `table_info.id` |
| `name` | VARCHAR(128) | 列名 |
| `type` | VARCHAR(64) | `bigint` / `decimal(18,4)` / `varchar(255)` / `datetime` |
| `role` | VARCHAR(32) | `primary_key` / `foreign_key` / `dimension` / `measure` |
| `description` | TEXT | 业务含义（进提示词） |
| `examples` | TEXT | JSON 数组，样例值（供 WHERE 参考） |
| `alias` | TEXT | JSON 数组，别名（建向量用） |

索引：`idx_column_info_dataset (dataset_id)`、`idx_column_info_table (table_id)`

> **为什么 id 是“表.字段”**：不同表常有同名列（id/name/status），必须全局唯一；
> 同时自带表名，`split('.')[0]` 就能反推表。
>
> **examples 与 alias 存 JSON 字符串**：迁移简单、兼容性好；代价是不能用 SQL 直接查数组。
> 建库时把 alias 的每一项单独向量化，同一字段在 Qdrant 里会有多条 point，但 `payload.id` 相同。

### 3.7 metric_info — 指标

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | VARCHAR(128) **PK** | `{dataset_id}:{指标名}`，如 `2:GMV` |
| `dataset_id` | INT **FK→datasets.id** | |
| `name` | VARCHAR(128) | GMV / AOV |
| `description` | TEXT | 业务口径 |
| `relevant_columns` | TEXT | JSON 数组，依赖字段 id |
| `alias` | TEXT | JSON 数组，别名 |
| `created_at` | BIGINT | |

索引：`idx_metric_info_dataset (dataset_id)`

> CSV 推断不出业务口径，指标需要用户配置或 LLM 生成后人工确认（需求 M4，P1）。
> MVP 先支持“字段级聚合”，指标缺失不阻塞主流程。

### 3.8 query_history — 问数审计

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INT **PK** AUTO_INCREMENT | |
| `user_id` | INT | 谁问的 |
| `dataset_id` | INT | 查的哪个数据集 |
| `question` | TEXT | 原问题 |
| `sql` | TEXT | 实际执行的 SQL |
| `hit_cache` | TINYINT | 0 / 1（精确或语义命中） |
| `rows_count` | INT | 返回行数 |
| `latency_ms` | INT | 端到端耗时 |
| `status` | VARCHAR(16) | `ok` / `error` |
| `error` | TEXT | 失败原因 |
| `created_at` | BIGINT | |

索引：`idx_history_user_time (user_id, created_at DESC)`、`idx_history_dataset (dataset_id)`

> 用途四合一：审计、命中率统计、慢查询分析、评测数据回流。
> 注意：`questions` 里可能有敏感信息，导出/展示时要脱敏（二期）。

### 3.9 物理表 `ds{dataset_id}_t{n}`

```sql
CREATE TABLE ds1_t0 (
  `order_id`  varchar(255),
  `region`    varchar(255),
  `amount`    decimal(18,4),
  `order_date` datetime
);
```

| 规则 | 说明 |
| --- | --- |
| 表名 | `ds{dataset_id}_t{序号}`，程序生成 |
| 列名 | CSV 表头清洗：非字母数字下划线替换为 `_` |
| 类型 | 整数 `bigint`、小数 `decimal(18,4)`、日期 `datetime`、其余 `varchar(255)` |
| 主键 | 不设（CSV 无可靠主键），需要时人工指定 |
| 索引 | 默认不建；后续按查询频率加 |

## 四、Qdrant 与 ES 的结构

### Qdrant（两个 collection）

```text
column_info_collection：字段向量
metric_info_collection：指标向量
```

| 项 | 值 |
| --- | --- |
| 向量维度 | 1024（embedding 模型决定） |
| 距离 | COSINE |
| point id | uuid（每条向量一个） |
| payload.id | 业务 id（同一字段的多条 point 共享） |

必要的 payload 字段（**过滤就靠这三个**）：

```json
{"user_id": 1, "dataset_id": 2, "datasource_id": 3, "id": "orders.amount", "table_id": "orders",
 "name": "amount", "type": "decimal(10,2)", "role": "measure", "description": "订单金额",
 "examples": ["199.00"], "alias": ["销售额"]}
```

```text
检索必须带 Filter(must=[user_id, dataset_id])，否则会跨用户召回
```

### ES（`value_index`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | keyword | 文档 id：`{dataset_id}:{column_id}:{value}` |
| `user_id` | keyword | 租户过滤 |
| `dataset_id` | keyword | 数据集过滤 |
| `column_id` | keyword | 属于哪个字段 |
| `value` | text（ik_max_word） | 被检索的取值 |

```json
{"id": "2:orders.region:华北", "user_id": "1", "dataset_id": "2",
 "column_id": "orders.region", "value": "华北"}
```

```text
查询 = bool.must[match value] + filter[term user_id, term dataset_id]
取值只同步低基数列，且 LIMIT 抽样（MySQL 直连必须限流）
```

### Redis（缓存 key）

```text
精确：sql:{user_id}:{dataset_id}:{schema_version}:{sha256(归一化问题)}
语义：sqlvec:{user_id}:{dataset_id}:{schema_version}（hash：问题hash → {vector, sql}）
```

## 五、规则（必须记住）

1. **多租户红线**：任何查询都要带 `user_id` / `dataset_id`；Qdrant/ES 必须加过滤条件；缓存 key 必须含租户。
2. **删除级联**：删数据集 → `dataset_tables` / `table_info` / `column_info` / `metric_info` / 物理表 / Qdrant 点 / ES 文档 / Redis key。
3. **schema 变更**：改元数据后 `dataset.schema_version += 1`；同时清掉该数据集的语义缓存。
4. **只读执行**：执行用户 SQL 用只读账号（`GRANT SELECT`）；元数据写入用可写账号。
5. **时间统一**：`BIGINT` 秒级时间戳，不用日期字符串。
6. **不存明文凭证**：`config_enc` 只能是密文；日志与接口返回都要脱敏。

## 六、迁移策略

```text
MVP：SQLAlchemy create_all（启动时建表），够用
二期：引入 alembic，每次 schema 变更写迁移脚本
物理表：不进迁移体系，脚本创建/删除
```
