## 问题修复

### 1. examples 缺失（采样）

**问题原因**

```text
MySQL 这条路径只做了"结构发现"，从来没做过"值采样"，代码里 examples 是写死的空列表。
```

**解决方案**

新增方法，并在 `_persist_schema` 处传入 samples，examples 初始化为 samples：

```python
async def _collect_samples(self, source, schemas) -> dict[str, list]:
    """采样低基数字段的示例值：{(表,字段): [值...]}，>50 个视为高基数跳过。"""
    samples: dict[str, list] = {}
    for schema in schemas:
        for col in schema.columns:
            try:
                rows = await source.execute(
                    f"SELECT DISTINCT `{col.name}` AS v FROM `{schema.name}` LIMIT 51",
                    limit=51,
                )
            except Exception as exc:  # noqa: BLE001 - 采样失败跳过该列
                logger.debug(f"采样 {schema.name}.{col.name} 失败: {exc}")
                continue
            values = [str(r["v"]) for r in rows if r["v"] is not None]
            if 0 < len(values) <= 50:
                samples[f"{schema.name}.{col.name}"] = values
    return samples
```

实测效果（dw，dataset 12）：

```text
21/24 字段有 examples（之前 0）
ES nl2sql_values: 253 条文档（之前 0）
date_id 因 90 个不同值 > 50 被跳过 ← 已知限制
```

`date_id` 这种字段里面存的是真实日期，返回三个月数据时 `date_id` 的 value 会有 90 个；
而采样逻辑是"基数超过 50 个直接跳过"（防止订单号这种进来），所以 `date_id` 被阈值挡掉了。

**解决方案：按语义放宽阈值**

```python
DATE_LIKE_KEYWORDS = ("date", "day", "month", "year", "quarter", "time", "dt")

@classmethod
def _sample_limit(cls, column_name: str) -> int:
    return 200 if any(k in column_name.lower() for k in cls.DATE_LIKE_KEYWORDS) else 50
```

```text
效果：23/24 字段有 examples；date_id 采到 ["20250101", ...]
```

### 2. 模型不知道日期字段用法

**问题原因**

```text
role 修好、JOIN 键能补进来之后，时间类仍然错：

t03「2025年第一季度销售额」
  → ON fact_order.date_id = dim_date.year      （拿外键去连年份列）

t08「2025年1月每天的订单数」
  → WHERE d.day BETWEEN '2025-01-01' AND '2025-01-31'
     （以为 day 是日期，实际是 1~31 的整数）
```

```text
根因：模型只知道"有个 int 字段叫 date_id"，不知道：
· date_id 是 yyyyMMdd 整数（20250101），不能当日期函数参数
· dim_date 已经把年/月/季度拆成 year / month / quarter
· 两个表的 date_id 才是同一维度，应该 date_id = date_id
```

**解决方案**

1.  merge 里用 LLM 推断表关系（不再用"同名 _id"这种硬编码规则）

```python
# 收集候选：只收 role=foreign_key / primary_key 的列
foreign_keys, primary_keys = [], []
for table in table_infos:
    for column in table["columns"]:
        item = {
            "column": f"{table['name']}.{column['name']}",
            "type": column.get("type", ""),
            "examples": (column.get("examples") or [])[:3],
        }
        if column.get("role") == "foreign_key":
            foreign_keys.append(item)
        elif column.get("role") == "primary_key":
            primary_keys.append(item)

# 单表 / 没外键 → 不花这次 token
if foreign_keys and primary_keys and len(table_infos) > 1:
    relations = await infer_relations(foreign_keys, primary_keys)
```

```python
async def infer_relations(foreign_keys, primary_keys) -> list[str]:
    prompt = PromptTemplate(template=load_prompt("infer_relations"), ...)
    chain = prompt | llm | JsonOutputParser()
    mapping = await chain.ainvoke({...})     # {"fact_order.date_id": "dim_date.date_id"}
    return [f"{fk} = {pk}" for fk, pk in mapping.items()]
```

**推断依据（写在 `prompts/infer_relations.prompt` 里）**

```text
1. 样例值格式/范围是否一致（20250101 这种日期编号 vs R001 这种地区编号）
2. 字段名是否同名或语义接近
3. 业务常识（订单表通常关联地区/客户/商品/日期维度）

输出：{"fact_order.date_id": "dim_date.date_id"}，判断不了的不要输出
```

```text
产出 → state["table_relations"] = ["fact_order.date_id = dim_date.date_id"]
```

2.  prompt 增加「表关联关系」段 + 字段约定

```text
表关联关系（JOIN 条件照这个写）：
{table_relations}

9. 字段约定：
   - 以 _id 结尾的是编号字段，不要当作日期/数值使用
```

### 3. prompt 聚合规则
**问题原因**
```text
问题：销量最低的品类是哪个
模型生成：SELECT category, MIN(order_quantity) ... GROUP BY category
正确：    SELECT category, SUM(order_quantity) AS q FROM ... GROUP BY category
          ORDER BY q ASC LIMIT 1
根本原因不是“模型不懂 SQL”，是没有“度量口径”这一层。
```
```text
· "销量" 是一个指标，不是一列
  它 = SUM(order_quantity)，而模型手里只有 order_quantity 这一列
· 如果metric_info 表是空的 → 没有指标定义可召回
· prompt 里也没有"比较类问题要先聚合"的规则
→ 模型只能按字面找最像的操作：MIN(order_quantity)

```
**解决方法**

加两条规则 + 一个口径表

在 `prompts/generate_sql.prompt` 的【任务要求】末尾追加：
```text
10. 比较/排名类问题（最高、最低、最多、最少、第一、Top N）：
    先确定比较对象对应的"度量口径"，再分组聚合，最后排序取数
    ✗ 错误：直接对明细列取极值，如 MIN(order_quantity)、MAX(order_amount)
    ✓ 正确：GROUP BY 维度 → 对度量聚合（SUM/COUNT）→ ORDER BY 聚合值 → LIMIT 1

11. 度量口径（遇到这些词按此聚合）：
    · 销量 / 数量 / 件数  → SUM(数量字段)
    · 销售额 / 金额 / GMV → SUM(金额字段)
    · 订单数 / 单量       → COUNT(订单号)
    · 客单价              → SUM(金额) / COUNT(DISTINCT 客户)
    · 平均订单金额        → AVG(金额字段)
```

### 5. qdrant别名
第一次测试,存qdrant别名的时候,没有传递别名,导致召回率下降,新建了创建别名方法,llm生成

别名是基于“字段名 + 类型 + 样例值”生成的。

不会影响延迟,因为是在图外面调用的,添加字段元数据表时调用

reindex是在添加完元数据后调用的


```python
async def generate_aliases(schema, samples: dict[str, list] | None = None) -> dict[str, list]:
    """返回 {字段名: [别名...]}，最多 3 个/字段。"""
    samples = samples or {}
    columns = [
        {
            "name": col.name,
            "type": col.type,
            "examples": (samples.get(f"{schema.name}.{col.name}") or [])[:3],
        }
        for col in schema.columns
    ]

    prompt = PromptTemplate(
        template=load_prompt("generate_aliases"),
        input_variables=["table", "columns"],
    )
    chain = prompt | llm | JsonOutputParser()
    try:
        result = await chain.ainvoke(
            {
                "table": schema.name,
                "columns": json.dumps(columns, ensure_ascii=False),
            }
        )
    except Exception as exc:  # noqa: BLE001 - 失败就用空别名
        logger.warning(f"生成别名失败 {schema.name}: {exc}")
        return {}

    if not isinstance(result, dict):
        return {}

    aliases: dict[str, list] = {}
    for name, values in result.items():
        if not isinstance(values, list):
            continue
        cleaned = [str(v).strip() for v in values if str(v).strip()]
        if cleaned:
            aliases[name] = cleaned[:3]
    return aliases
```

#### 2.  结果自检 
为什么`correct_sql`不够还要检查?

因为两者触发条件不同：`correct_sql` 修“跑不通”，`check_result` 修“跑通了但答错”。

为什么 `correct_sql` 兜不住 t08错误

```sql
-- t08 生成的 SQL
SELECT d.day, COUNT(f.order_id) AS 订单数
FROM fact_order f JOIN dim_date d ON f.date_id = d.date_id
WHERE d.year = 2025 AND d.month = 1
GROUP BY d.day
```
```text
· 语法正确 ✅
· 字段都存在 ✅
· 执行成功，返回 31 行 ✅
· 数据库不会报任何错
→ correct_sql 根本不会被触发（没有错误可修）
```
但答案是错的：模型按 day（1~31）分组，而不是按具体日期。数据库无法判断“用户想要哪种”。

还有就是SQL 跑通但返回 0 行 
```text
数据库认为这是正常结果
但很可能 WHERE 写错了（date_id 用了 DATE_FORMAT）
→ 也只有自检能发现
```

**解决问题**

核心思路：用“问题 + SQL + 结果”做规则校验，可疑就带着原因回 correct_sql 重试一次。

现在的实现的 `check_result` 只查两件事
```text
if not rows: 可疑
if 所有值都是 None: 可疑
```
加四条规则
```python
"""结果自检：判断“能跑”之外，答案是否合理。"""

import re

from langgraph.runtime import Runtime

from app.agent.context import Nl2SqlContext
from app.agent.state import Nl2SqlState


def _group_by_clause(sql: str) -> str:
    """只取 GROUP BY 子句，避免 WHERE 里的 date_id 干扰判断。"""
    m = re.search(
        r"group\s+by\s+(.+?)(?:\s+order\s+by|\s+limit|\s+having|$)",
        sql,
        re.IGNORECASE | re.DOTALL,
    )
    return m.group(1).strip() if m else ""


def _check_daily(question: str, sql: str) -> str | None:
    """① 按天统计：GROUP BY 必须是日期字段。"""
    if not re.search(r"每天|每日|按天|按日|逐日", question):
        return None
    group = _group_by_clause(sql)
    if not group:
        return "问句要求按天统计，但 SQL 没有 GROUP BY"
    if not re.search(r"date_id|order_date|[\w.]*_date\b|datetime", group, re.IGNORECASE):
        return f"问句要求按天统计，但 GROUP BY 用的是 {group[:40]}，不是日期字段（应按日期编号分组）"
    return None


def _check_ranking(question: str, sql: str) -> str | None:
    """② 极值/排名：必须先分组聚合，再 ORDER BY + LIMIT。"""
    if not re.search(r"最低|最高|最多|最少|第一|top\s*\d|排名", question, re.IGNORECASE):
        return None
    s = sql.lower()
    if ("min(" in s or "max(" in s) and "group by" not in s:
        return "问的是分组后的极值/排名，应先 GROUP BY 聚合再排序，不能直接对明细列取 MIN/MAX"
    if "group by" in s and "order by" not in s:
        return "分组比较类问题缺少 ORDER BY（以及 LIMIT 1）"
    return None


def _check_ratio(question: str, rows: list[dict]) -> str | None:
    """③ 比例类：结果应在 0~1（或 0~100 且带 %）。"""
    if not re.search(r"占比|比例|率", question):
        return None
    for row in rows:
        for value in row.values():
            if isinstance(value, (int, float)) and value > 100:
                return "问的是比例，但结果大于 100，可能没有除以总数"
    return None


def _check_time_empty(question: str, rows: list[dict]) -> str | None:
    """④ 时间条件后为空：多半是日期字段用法错。"""
    if rows:
        return None
    if re.search(r"20\d{2}\s*年|20\d{2}-\d{2}", question):
        return "结果为空，检查时间条件：date_id 是 yyyyMMdd 整数，应按 year/month 过滤或 date_id = 20250101"
    return None


def _suspect_reason(state: Nl2SqlState) -> str | None:
    rows = state.get("rows") or []
    question = state.get("question", "")
    sql = state.get("sql", "")

    # 0）原有两条：空结果 / 全 NULL
    if not rows:
        return "结果为空，可能是筛选值或时间范围写错"
    first = rows[0]
    if first and all(v is None for v in first.values()):
        return "所有字段为空，可能是 JOIN 条件错误"

    # ①~④ 结构化规则
    for reason in (
        _check_daily(question, sql),
        _check_ranking(question, sql),
        _check_ratio(question, rows),
        _check_time_empty(question, rows),
    ):
        if reason:
            return reason
    return None
```

**现象**

#### bug 4:改数据源配置后仍用旧引擎

**原因**
```python
# registry.py
key = (user_id, datasource_id)
cached = self._cache.get(key)
if cached is not None:
    return cached          # ← 直接返回旧的 MySQLDataSource 对象
```
```text
因为数据源配置是在创建数据源的时候存的,建缓存的时候直接从元数据表里拿配置,如果数据源配置改了,用就引擎连接不上
```
**修法**

`app/datasources/registry.py` 新增 invalidate()
```python
async def invalidate(self, user_id: int, datasource_id: int) -> None:
    """数据源配置变更 / 删除后调用：踢掉缓存并释放连接池。"""
    key = (user_id, datasource_id)
    source = self._cache.pop(key, None)
    if source is None:
        return
    engine = getattr(source, "engine", None)
    if engine is not None:
        await engine.dispose()
```
datasources 路由的删除接口调用它

```python
async def delete_datasource(..., registry: DatasourceRegistryDep) -> dict:
    async with session.begin():
        result = await service.delete(user_id, datasource_id)
    await registry.invalidate(user_id, datasource_id)
    return result
```
再加一个修改数据源配置接口

内部会先测试连接然后,更新
```python
@router.put("/{datasource_id}")
async def update_datasource(
    datasource_id: int,
    body: DataSourceUpdateRequest,
    user_id: CurrentUser,
    session: SessionDep,
    service: DatasourceServiceDep,
    registry: DatasourceRegistryDep,
) -> dict:
    """改名字或连接配置；传了 config 会先测连接。"""
    async with session.begin():
        result = await service.update(
            user_id,
            datasource_id,
            name=body.name,
            config=body.config.model_dump() if body.config else None,
        )
    if body.config is not None:
        # 配置变了，踢掉进程内缓存的连接池，避免继续用旧引擎
        await registry.invalidate(user_id, datasource_id)
    return result
```

### 本轮发现并修复的问题

#### 1. 指标写接口没开事务（数据被回滚）

**现象**

```text
POST /api/datasets/26/metrics 返回 201
但 SELECT * FROM metric_info → 0 行；GET 列表也是空
```

**原因**

```text
get_session 不再自动 commit（改成用例级事务后）
指标路由忘了写 async with session.begin()
→ 提交的 201 是假的，session 关闭时全部回滚
```

**修复**

```python
async with session.begin():
    return await service.save_metric(...)
```

#### 2. 指标建议的 prompt 花括号冲突

**现象**

```text
POST /api/datasets/{id}/metrics/suggest → 500
pydantic ValidationError: Invalid variable name '表名.字段名'
```

**原因**

```text
PromptTemplate 用 f-string 语法
prompt 里写了 {表名.字段名} 和 {t_ord.amt} 作为示例
→ 被当成模板变量，且变量名里含点号，直接报错
```

**修复**

```text
prompt 里所有字面量花括号改成双花括号（{{ }}）
只有 {schema} 保持单花括号
```

#### 3. m12：日期列根本没进 prompt（最值得记的一个）

**现象**

```text
问题："2025年1月的订单数是多少"
生成（多次，写法每次不同）：
  WHERE ord_no LIKE '202501%'
  WHERE STR_TO_DATE(CONCAT('2025-01-', SUBSTR(ord_no, 3, 2)))
  WHERE ord_date BETWEEN ...
  WHERE t_ord.date_id BETWEEN ...
结果恒为 0 或报 Unknown column
```

**排查**

```text
临时在 generate_sql 打印进 prompt 的字段：
  DEBUG_COLUMNS t_ord:['ord_no']        ← dt 不在里面！
```

**根因链**

```text
① merge 只补主外键（role = primary_key / foreign_key）
   dt 的 role 是 dimension → 不在补齐范围
② 向量召回没召回 dt（问题里没有"日期"字样）
③ filter_table 只能从已有候选里裁，凭空补不回来
④ 模型要按"2025年1月"过滤，手上却没有日期列
   → 拿订单号硬造日期
⑤ 自检的"空结果"规则不触发：COUNT 返回的是一行 0，不是空数组
```

**修复（五处）**

```python
# ① merge：补日期类字段（date/dt/time/day/month/year）
for column in await meta.list_columns_by_table(dataset_id, table_id):
    if re.search(r"date|dt|time|day|month|year", column.name, re.I):
        cols.append(...)

# ② filter_table：问题含时间词时，强制保留日期列
has_time_word = re.search(r"\d{4}\s*年|\d{1,2}\s*月|今天|本月|上个月|季度", question)
if column["name"] in wanted or (has_time_word and date_like.search(column["name"])):
# 且metric 的 relevant_columns也要在filter_table强制保留

# ③ prompt：不再绑死 date_id，明确"日期字段名以表结构为准"
- 时间过滤只能作用在表结构里真实存在的日期字段（可能叫 dt / date_id / order_date，禁止照抄示例）
- 禁止用订单号、编号、ID 这类字段做时间过滤或日期解析

# ④ check_result 第 5 条规则
· 列与日期字面量比较但不是日期列 → 可疑
· 日期函数作用在非日期列上（STR_TO_DATE(ord_no)）→ 可疑
· 聚合结果只有一行且为 0 → 可疑

# 5 自检规则从"按名字猜日期列"改成"查 column_info.type"
DATE_TYPES = ("date", "datetime", "timestamp", "time")

def _is_date_column(column: str, types: dict[str, str] | None = None) -> bool:
    column_type = (types or {}).get(column.lower(), "").lower()
    if any(token in column_type for token in DATE_TYPES):
        return True
    return bool(DATE_LIKE.search(column))     # 兜底：int 存 yyyyMMdd 的字段
```

**修复后**

```text
m12：SELECT COUNT(t_ord.ord_no) FROM t_ord WHERE t_ord.dt BETWEEN 20250101 AND 20250131
→ 22，与 gold 一致
DEBUG 确认：t_ord:['ord_no', 'dt']
```

#### 4. 缓存会掩盖修复（再次踩到）

```text
改完代码直接问同一个问题，仍返回旧 SQL
→ Redis 精确缓存命中（key 含 dataset_id + schema_version）
→ 指标写操作会 bump schema_version，但纯 prompt/规则改动不会
结论：改生成行为后必须 --flush-cache
```

### 结论

```text
· 指标功能可用：口径被严格遵守、别名能召回、可与条件组合，12/12 全通过
· "客单价"与"平均订单金额"没有混淆，说明指标召回 + prompt 注入这条链是通的
· 指标类问题的真正难点不在指标本身，而在"依赖字段是否进了 prompt"
  （日期列没召回 → 模型只能编）
· 自检规则要覆盖"结果为 0"和"字段类型用错"，只判空数组不够
```



现在check_result有七条规则

| # | 规则 | 触发条件 | 返回值（给 correct_sql 看） |
| --- | --- | --- | --- |
| 0 | 空结果 | `rows` 为空 | 结果为空，可能是筛选值或时间范围写错 |
| 0 | 全 NULL | 第一行所有值都是 `None` | 所有字段为空，可能是 JOIN 条件错误 |
| ① | 按天没按日期分组 | 问句含"每天/每日/按天/按日"，但 GROUP BY 里没有日期字段 | 问句要求按天统计，但 GROUP BY 用的是 d.day，不是日期字段 |
| ② | 极值/排名口径错 | 问句含"最高/最低/最多/最少/第一/Top N/排名"，且 ①直接 MIN/MAX 没有 GROUP BY ②有 GROUP BY 但没有 ORDER BY | 应先 GROUP BY 聚合再排序，不能直接对明细列取 MIN/MAX |
| ③ | 比例越界 | 问句含"占比/比例/率"，且结果值 > 100 | 问的是比例，但结果大于 100，可能没有除以总数 |
| ④ | 时间过滤后为空 | `rows` 为空 且 问句含 `20xx年` / `20xx-xx` | 结果为空，检查时间条件：date_id 是 yyyyMMdd 整数，应按 year/month 过滤 |
| ⑤ | 时间条件打在非日期列上 | 见下（三种情况任一命中） | 时间条件作用在非日期字段 ord_no 上，应该用日期字段做范围过滤 |

规则 ⑤ 内部有三个判断：
```text
1) 日期函数包了非日期列：MONTH(ord_no) / STR_TO_DATE(ord_no)
2) 跟日期字面量比较的不是日期列：ord_no >= '2025-01-01'
3) 聚合结果只有一行且为 0（多半过滤条件打错）
```
